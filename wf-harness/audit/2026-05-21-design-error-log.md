# Wealth Factory Harness Design Error Log

Date: 2026-05-21
Phase: Design kickoff and first harness slice implementation

## Purpose

Capture design-stage mistakes, false assumptions, and pressure-test lessons so they are not repeated in the custom harness effort.

## Known Lessons Imported From The Prior Build

1. Paperclip proved the concept but became the sustained hotspot under commercial-style soak.
2. Queue reliability does not guarantee execution-engine reliability.
3. Tenant safety, fairness, and backpressure must be first-class system rules.
4. Tenant-facing UX should stay calm and structured; backend chatter is not product value.
5. BYOK must remain in Wealth Factory, not leak into the execution engine boundary.
6. Recovery from interruption must be based on persisted state, not conversation memory.

## Current Design-Stage Risks To Avoid

1. Recreating Paperclip's weak spots by copying implementation literally instead of mirroring behavior intentionally.
2. Letting child personas talk directly to each other and causing uncontrolled drift.
3. Allowing uncontrolled dynamic card creation until the board becomes unreadable.
4. Building a dashboard that exposes backend execution details instead of meaningful progress.
5. Turning the new harness into a broad "agent OS" instead of a bounded Wealth Factory orchestration slice.

## Phase 1 Implementation Lessons

1. The first board cut looked polished but was still a static demo. Reviewer feedback correctly forced the board route and page off fixtures and onto a tenant-scoped persisted path.
2. Harness HTTP cannot collapse all failures into `401 unauthorized`; internal failures must stay distinguishable from auth failures or operators will chase the wrong problem.
3. `WF_HARNESS_ENABLED_WORKFLOW_IDS` is not meaningful until a live runtime path actually consumes it. Configuration alone is not progress.
4. Persisted run/card/event tables are only valuable if the slice really writes and reads them. Repository scaffolding without a live caller is false comfort.
5. The intentional E2E fail step can poison the pass step if a dummy server is not fully cleaned up. A stray Python listener on `127.0.0.1:5173` produced false directory-listing failures until it was killed.
6. PowerShell separator quirks remain real on this machine. Prefer native sequential commands and explicit cleanup over bash-style chaining.
7. Browser fallback data must stay loopback-only. A polished fake CEO/CFO board is useful for static local shell work, but it becomes a dangerous false green if remote or authenticated paths can silently keep showing it after API/auth failures.
8. Tenant/package access denials and infrastructure faults cannot share the same generic error path. The harness board must fail closed on missing membership or package entitlement without masking DB outages as `401 unauthorized`.
9. A narrow route expansion still needs the surrounding type surface updated immediately. Adding proposal approval behavior without extending the handler option type broke `tsc` even though the runtime logic was correct.
10. Persisted CEO approvals need a real table, not just events. Proposal identity, pending status, and idempotent approval are too fragile if they are inferred from card-event history alone.
11. PowerShell path expansion is not the same as shell glob expansion. Targeted `rg` scans should use explicit file lists or `--glob` filters, not raw `tests/harness-*.test.ts` path arguments, or the scan itself becomes a false sharp edge.
12. Proposal approval ordering has to respect the real database contract, not just the in-memory repository. When an approval row references a newly created child card, the foreign key must either be deferred inside the transaction or the mutation order must change accordingly.
13. Approval mutations are not safe as an optional best-effort multi-step write path. If a future harness mutation needs multiple writes to stay consistent, require an atomic runner explicitly instead of normalizing non-transactional usage in tests or public service construction.

14. A stale .git/index.lock can linger after interrupted git operations on this machine. Clear it explicitly before staging instead of retrying blindly or assuming another live git process is still running.
15. Replacing fake seeded persona lanes with one real persisted CEO-driven create-card seam is more valuable than adding a generic state-editing API around bootstrap theater. Remove fake execution at the source before broadening mutation surface.
16. The current dashboard HTTP request shape only exposes query parameters, headers, and body size. A narrow guarded write route can use query params temporarily, but broader harness mutations will eventually need parsed JSON-body support to keep the contract clean.
17. On this machine, parallel `npm` invocations can fail with `UNKNOWN: unknown error, read` against `package.json` even when the file is healthy. Treat that as a local tooling sharp edge and rerun the verification gate sequentially instead of assuming the repo is broken.
18. The old "occupy port `5173` with a dummy listener" E2E fail trick is no longer reliable on this machine. When the listener does not truly bind, Playwright can still reuse the real dev server and produce a false pass. Verify the failure mechanism itself before trusting the fail-then-pass proof.
19. Tightening Playwright with an intentionally impossible timeout is a reliable local fail trigger for the harness gate when the dummy-listener method is flaky. Log the method explicitly so later phases do not waste time rediscovering it.
20. Mutation paths that can seed a run on first use must not re-enter `runAtomically` from inside an already-open atomic block. The in-memory harness repository will hide that mistake unless a nested-atomic guard test exists.
21. Direct child-card creation needs at least narrow idempotency and an open-card cap from day one. Otherwise double submits and retries can create card sprawl long before richer CEO policy logic is built.
22. The deferred approval-card foreign-key seam needs 2 separate proofs. First, prove the approval update and child-card insert share one leased transaction client and roll back together on failure. Later, prove the actual deferred foreign key against a real migration-backed Postgres transaction. Do not collapse those into one claim.
23. On this Windows machine, overlapping GitNexus FTS/cypher calls right after `gitnexus analyze` can briefly lock `.gitnexus\\lbug`. Serialize GitNexus preflight commands before assuming the repo index is unhealthy.
24. The real Postgres harness proof is easiest to trust when it applies only the harness migrations plus a tiny `wfpc.tenants` prerequisite table in an isolated disposable database. Pulling in more schema than the seam actually needs just increases noise and setup fragility.
25. Docker-backed proof tests should not block the Vitest worker thread with long `execFileSync` calls. On this machine that caused `[vitest-worker]: Timeout calling "onTaskUpdate"` even when the DB logic was correct; async child-process helpers keep the proof green.
26. Unsupported harness child-card state strings must fail as bounded client input, not bubble into `500 service_unavailable`. Validate the enum at the HTTP seam and keep the service conflict-aware too.
27. Tenant-authored outcome summaries should not travel through URL query strings. Until the dashboard HTTP contract grows parsed request bodies, keep summary recording off the public advancement URL surface.
28. Run-level progression should be derived from persisted card/proposal state, not implied from bootstrap or UI assumptions. The safe early precedence is `working -> waiting -> blocked -> assembling`, and final `done` should stay explicit until assembly/completion logic is real.
29. Harness audit expansion must stay metadata-only for tenant business content. Publish mutation and reconciliation events through the durable audit sink, but keep raw `resultSummary` text out of audit payloads and use booleans/state metadata instead.
30. Post-commit audit publishing must not turn a committed harness mutation into an apparent failure. If the durable audit sink is down, the mutation should still return success and emit a warning instead of encouraging retries against already-persisted state.
31. Once the harness starts accepting richer mutation input, move it to parsed JSON bodies instead of query parameters. Keep tenant-authored business text off URL surfaces and keep the write API command-style instead of turning it into a generic board editor.
32. Final completion should stay CEO-gated and explicit. Let child-card progression derive `assembling`, then require a separate persisted completion command for `done` instead of inferring business completion from internal motion.
33. Card-discipline policy should grow in narrow workflow terms, not abstract editing terms. Blocking duplicate open deliverable lanes is a useful next step; broader deny/defer or lane-merging logic should wait until the current policy seams are proven.
34. Request-body guardrails belong in the Node adapter as well as the handler. If the adapter trusts only `Content-Length`, chunked or mismatched payloads can bypass the size limit after the whole body is already buffered into memory.
35. Rate-limiter client IPs need trusted-proxy awareness. Loopback reverse proxies should be allowed to forward the first client IP, but untrusted remote peers must not be able to spoof limiter identity through `x-forwarded-for`.
36. Dashboard auth and internal failure paths cannot share the same public status code. If downstream faults are flattened to `401`, operators lose the signal that the runtime is unhealthy and tenants get misleading auth errors.
37. A single implicit harness workflow selector is only safe while one workflow is enabled. If multiple harness-eligible ids can surface, fail closed until an explicit selector exists instead of silently letting config order choose the run target.
38. Proposal approval must prove tenant ownership before taking any idempotent shortcut. An already-approved proposal is still sensitive tenant state, and returning its card id before the tenant check leaks foreign run metadata.
39. Bounded persona/deliverable policy has to exist at the service seam, not only in UI conventions. Otherwise the direct child-card mutation path becomes an uncontrolled taxonomy surface and invites lane sprawl.
40. Storage OAuth availability should degrade per provider, not globally. Missing Dropbox config should not disable Google Drive, and disabled routes still need security/CORS headers so browsers receive a real `503` instead of a network-shaped failure.
41. Provider-specific OAuth callback routes must be enforced as part of callback integrity. If callback completion trusts only `state`, a miswired redirect URI or proxy rewrite can silently complete the wrong provider flow instead of failing closed.
42. `WF_STORAGE_OAUTH_REDIRECT_ORIGIN` cannot be an arbitrary host override. Validate it as a bare http(s) origin and require it to already exist in `WF_ALLOWED_ORIGINS` before building callback URLs.
43. Route classification must happen before harness rate limiting. Unknown proposal-like paths should return `404` without consuming the approval bucket or distorting traffic signals.
44. After validating an origin-shaped config value, store the normalized origin, not the raw string. Otherwise a trailing slash can pass validation and still produce a broken exact-match redirect URI later.
45. Provider-mismatch OAuth callbacks should fail closed without burning the pending state. A wrong callback path should be a recoverable rejected attempt, not a one-shot denial of the tenant's connector flow.
46. Once proposal policy starts widening, old tests that expect every duplicate lane to hard-fail become misleading. The intended bounded behavior is now "reuse an existing lane when it is the same work, collide only when another active owner would make the result ambiguous."
47. Disposable Postgres proof paths must track the same migration chain as the live repository contract. Adding new proposal columns without updating the disposable test database created a false failure that looked like a repository bug but was really a migration-harness drift issue.
48. `exactOptionalPropertyTypes` is a real seam in this repo. Repeated helper calls embedded directly into object spreads can still widen to `string | undefined` and fail `tsc`, so narrow optional command inputs into local variables before building handler payloads.
49. When mapping widened proposal rows back into runtime types, build the base object first and assign optional fields conditionally. Returning one large conditional-spread literal can look fine in JavaScript while still violating TypeScript's exact-optional-property rules.
50. A `defer` state that disappears from the board is functionally a hidden deny, not a pause. If a workflow decision is meant to be revisitable, keep it in the read model and let the decision seam reopen it later.
51. Reusing an existing lane still needs a visible parent-lane approval trail. If the originating card loses all evidence that its proposal was accepted, the board feels like it dropped work even when the child lane correctly absorbed it.
52. Once the board starts firing live contract actions, browser errors must stay structured. Flattening `conflict`, `rate_limited`, or `invalid_request` into one generic client failure string recreates the same assumption-heavy debugging posture that hurt Paperclip under pressure.
53. Rich board rendering should not bias only toward the main CEO-review branch. `resolve-attention` needs its own fixture-level coverage too, or resume/unblock controls can silently fall behind while final-assembly actions stay polished.
52. Repeated sub-card requests need an older-request rule or they will keep pretending to be fresh work. The bounded fix is to prefer active-lane reuse and valid handoff first, then reuse the latest earlier unresolved governance hold for the same request title/persona/deliverable triple, and only create a new lane when neither of those guards applies.
53. The `approveProposal()` helper alias is intentionally narrower than `decideProposal(... decision: "approve")`. If the engine now resolves an approve request to `deferred` or `denied`, tests must call `decideProposal` directly or they will false-red with `Harness proposal approval did not produce a lane target`.
52. When two HTTP endpoints share one underlying decision command, keep their semantics distinct. `/approve` should not be allowed to return `200` for a non-approved terminal status just because the deeper command can express more than one decision.
53. Governance history should not be reconstructed from comment events after the fact. Once the harness needs durable board memory, write an explicit append-only decision ledger in the same transaction seam as the business mutation.
54. A deliverable-owner collision is not the same thing as a malformed request. When another active persona already owns the deliverable lane, the bounded CEO behavior is to defer and keep the proposal visible rather than throw a low-level conflict that hides the governance choice.
55. PowerShell plus Vitest has its own false-red path on this machine: `--runInBand` is a Jest habit, not a valid Vitest flag here. Use the repo's native `vitest run ...` form or the proof step can fail before any tests actually execute.
56. Once a board-decision ledger exists, keep the public read model bounded. Raw `decisionNote` text is useful for internal governance context, but replaying it directly into `recentDecisions` turns the board into a free-form note stream and weakens the “not a generic editor” boundary.
57. New migration helpers should re-check schema readiness after applying a create-if-missing migration. Otherwise a partially drifted table can survive `create table if not exists` and the helper will look successful until the first live repository call fails.
58. CEO completion summaries should have one durable business-result home. Store the full summary on the CEO result event, and keep the board-decision ledger metadata-only enough that it does not become a second competing source of truth.
59. Board-memory widening should ride on the existing append-only decision ledger, not a new free-form memory store. If the harness needs richer governance context, add bounded fields and derived read-model views before considering a second persistence surface.
60. Exact-optional TypeScript settings can turn a harmless-looking helper call into a false red if an optional board field is rebuilt inline. Narrow optional package-note values into local variables before spreading them into response objects.
61. A deferred approval without a visible reason is only half a governance feature. If the board pauses a request, the read model should explain why it is paused and what condition reopens it, without replaying raw internal notes.
62. Repeated defer decisions can create the same kind of board noise as duplicate lane opens. If the CEO has not changed the note or decision context, treat the second defer as idempotent and keep the governance ledger quiet.
63. Tenant-facing completion packaging needs a structured governance item view, not just counts and flat objection strings. Deferred and denied requests should surface as bounded items with labels, recommendations, objections, and review triggers derived from ledger metadata rather than raw notes.
64. GitNexus can report `LadybugDB unavailable` on Windows immediately after a fresh analyze because `.gitnexus\\lbug` is briefly locked. That is a tooling sharp edge; wait or serialize the next GitNexus call instead of assuming the repo index is broken.
65. The intentional Playwright fail step and the real pass step must never run in parallel. Two Playwright invocations will compete for the same Vite web-server lifecycle on `127.0.0.1:5173`, and the second run can lose the server mid-suite with false `ERR_CONNECTION_REFUSED` failures.
66. On this machine, `docker --version` is not a strong enough readiness check for the disposable Postgres proof. The CLI can exist while the Docker daemon pipe is unavailable, which causes a false-red image pull failure inside Vitest. Gate the proof on `docker info` success, not just the CLI binary.
67. Reused-lane approvals need structured lane state, not only approval comments. If folded follow-on work is stored only as `comment_added`, the board loses actionable continuity even though the CEO made a valid reuse decision.
68. Free-form CEO `decisionNote` text belongs in internal governance state, not in the tenant-facing activity feed. If proposal decisions reuse `comment_added` with the raw note, the board silently violates its own bounded-memory contract.
69. A run with no live child work should not fall back to `active` just because no child is `done`. When every non-CEO child lane is terminal-but-cancelled and no proposals remain, the truthful derived state is `blocked`, not fake progress.
70. Fresh-cycle behavior needs an explicit command mode once both "reopen bounded deferred work" and "start clean" are valid product moves. Hiding that choice behind one implicit behavior makes the CEO less intentional and forces policy debates into code branches instead of the mutation contract.
71. Progression-heavy harness tests are easy to poison when copied between slices. If a fixture accidentally repeats `working` or skips the `approved -> working` step before `done`, the suite false-reds the orchestration seam even though the runtime policy is fine.
70. Bounded public governance messages still need to preserve the real policy reason. Replacing every denied request with the same workflow-boundary text hides whether the CEO actually denied it for lane pressure, owner conflict, or true scope guardrail reasons.
71. If the board tells tenants to wait until an owner can \"clear or hand off\" a lane, that should map to a real bounded engine action. Governance copy that promises a handoff path without any executable handoff seam becomes misleading product behavior.
72. If a guarded mutation accepts a lane-targeting hint, the read model must surface the same bounded target and stale hints must fall back safely. The first handoff seam took `targetCardId` on writes without exposing a matching board hint, which let clients guess wrong and create avoidable hard conflicts.
73. Completed board cycles need an explicit follow-on policy across every lane-opening seam, not only proposal approval. Letting `assembling` or `done` runs fall through either normal proposal approval logic or direct CEO child-card creation reopens work implicitly and leaves terminal runs inconsistent.
74. If the board needs to show what governance actually implemented, derive that from the decision ledger instead of card activity. `comment_added` and other lane chatter are too presentation-oriented and too close to free-form notes to serve as trustworthy long-memory follow-through.
75. Packaged runs need an explicit follow-on seam instead of quietly reopening work in place. Starting a new persisted run for the next board cycle keeps terminal runs truthful and gives completed-cycle follow-through a bounded recovery path.
76. Policy-sensitive tests should not rely on helper behavior they are trying to distinguish. The first fresh-cycle proof accidentally used live defer logic for both branches, which made an alternate `lane_cap` case look like a carry-forward defect until the fixture pinned the non-reopenable decision explicitly.
77. Repeated unresolved proposal retries need a latest-earlier-request rule or they still sneak around card discipline. If the same request title/persona/deliverable is already unresolved, reuse the newest earlier unresolved governance hold after checking for active-lane reuse and valid handoff first.
78. The narrow `approveProposal()` helper is a false friend once `approve` can legitimately resolve to `deferred` or `denied`. Tests proving the wider decision seam must call `decideProposal(... decision: "approve")` directly or they will false-red waiting for a lane target that should not exist.
79. Small continuity memory should not be rebuilt forever from presentation events. Once absorbed follow-on work and latest outcomes matter for resume truth, promote them into a bounded per-lane continuity snapshot instead of scanning `proposal_absorbed` and `result_recorded` history on every board read.
80. Continuity memory is not a second governance ledger. Keep it operational, keep it per-card, and keep it transaction-local with the mutation that changed the lane so it never drifts into free-form notes or stale follow-through.
81. Bounded continuity still needs deterministic merge semantics in every repository implementation. If the board reads `absorbedWorkItems.at(-1)` as the newest resume clue, Postgres cannot merge with unordered `distinct` output or ignore the six-item cap while the in-memory repository stays ordered and bounded.
82. Owner-conflict handoff continuity must track the prior lane owner/title, not just the requesting persona/title. Those values can diverge, and if continuity snapshots attribute the handoff to the wrong source the tenant-facing board copy becomes subtly false even while the mutation technically succeeds.
83. A continuity field that is written but never hydrated back into runtime is just presentation fluff. If the engine room is supposed to resume live lane focus after interruption, continuity has to travel through `resumeRun(...)` alongside cards and proposals rather than staying trapped in board-read helpers.
84. Once continuity becomes the real resume directive, coalescing old values forever is the wrong default. The safe behavior is to overwrite `continuitySummary` intentionally on each continuity upsert so done/cancelled lanes can clear stale instructions and in-flight mutations can refresh the lane's next bounded move on purpose.
85. A done transition cannot accept a new resume directive just because the transport can carry one. If `resumeSummary` is allowed on a `done` write, the continuity seam will contradict its own terminal-lane rules and a stale restart instruction can override the completed-lane snapshot.
86. Runtime continuity is only valuable if a live engine seam actually consumes it. Hydrating `resumeFocus` into a worker-side lane-dispatch payload is a good narrow next step; stopping at board-read helpers or runtime-only test access leaves the continuity seam as expensive presentation memory rather than execution truth.
87. The first live worker-side harness path should stay intentionally narrow. Select one actionable non-CEO lane from persisted run/card/proposal/continuity state and emit a bounded dispatch payload; do not jump straight from continuity hydration to a generic multi-lane planner or free-roaming swarm behavior.
88. Worker dispatch cannot bypass the CEO approval gate. If `planning` child lanes are treated as actionable, the worker seam silently reopens pre-approval work that the board still describes as being shaped by the orchestrator.
89. A null worker dispatch should stay quiet all the way through the runtime seam. Returning `laneExecution: null` is not enough if the worker still emits a lane-dispatch event or records fake queued status for a terminal or non-actionable harness run.
90. Worker-side harness progress needs a durable claim boundary before it can be trusted. Selecting a lane without atomically moving `approved -> working` recreates the same kind of false-progress ambiguity Paperclip gave us under pressure.
91. The current `queued` child-lane state is still intentionally non-executable in the worker seam. Treating `queued` as actionable would silently bypass the CEO approval boundary and blur the difference between staged work and executable work.
92. GitNexus preflight is still worth doing even when Windows tooling is grumpy. If `gitnexus analyze` times out or Ladybug/PowerShell gets flaky, fall back to `E:\GitNexusHome\tools\gitnexus-fts-query.mjs` for seam orientation instead of skipping the structural map.
93. A worker claim without the surrounding durable facts is still only half a start seam. If the worker can move `approved -> working`, it should also record the `state_changed` event, refresh continuity to the active-lane resume summary, and reconcile run state in the same bounded mutation path.
94. Transactional worker tests need one shared harness-repository mock per test case. Once the worker start seam goes through a transaction wrapper, assertions aimed at the pre-transaction repo instance become false reds even when the live path is correct.
95. A worker-private lane outcome seam still needs compare-and-set protection. Reusing a generic `updateCardState` write would let a stale worker overwrite a lane that had already moved, so the bounded outcome path must transition from an expected `working` state or fail closed.
96. A private worker outcome is not complete if it only changes state. `done` outcomes also need the bounded `result_recorded` event plus continuity refresh, or the engine quietly recreates the same “progress happened somewhere else” ambiguity we were trying to leave behind with Paperclip.
97. The real Postgres continuity upsert must preserve `latestResultSummary` when a follow-up write only extends absorbed-work history. The in-memory repo already did that; Docker-backed proof caught the SQL path silently nulling the summary until the upsert used `coalesce(excluded.latest_result_summary, existing.latest_result_summary)`.
98. Multi-step worker execution should still stay one-lane-at-a-time. The safe next step after a private lane outcome is to claim at most one next `approved` lane in the same atomic seam; anything broader starts drifting back toward the ambiguous swarm-style runtime behavior that made Paperclip hard to trust under pressure.
99. A follow-on worker dispatch without a guarded workflow-status transition leaves the engine half-truthful. If the worker claims and emits the next lane, the runtime should also record that the workflow is still `running`; otherwise downstream status observers can lag behind the actual harness execution chain.
100. “Same lane refinement” has to be an explicit engine seam, not just a documentation promise. Reusing open lanes was not enough; without a bounded reopen path for recently completed same-persona/same-deliverable work, the harness would still force duplicate cards or fresh-cycle hops for small refinements that should preserve lane continuity.
101. The same-lane refinement rule has to apply to CEO-created child lanes too, not only proposal approvals. If direct child creation still treats a just-finished bounded assignment like brand-new work, the engine quietly reintroduces the duplicate-lane sprawl that the proposal path already learned to avoid.
102. Exact title matching is too brittle for lane classification. Small wording changes like `price` vs `pricing` can still be the same bounded assignment, so reuse/reopen and unresolved-request dedupe need a normalized title matcher or the harness will reintroduce duplicate-lane pressure for copy-only variations.
103. Direct CEO lane creation cannot stay stricter than proposal approval on active same-persona/same-deliverable work. If proposal approval can already fold follow-on work into an open lane, the direct CEO path should do the same with bounded continuity instead of throwing a conflict and forcing the board into avoidable duplicate-lane friction.
104. Harness workflow status cannot stay `running` just because a worker committed one lane outcome. If no follow-on lane is claimed, the worker must still write a non-running workflow status derived from the reconciled harness run state or the queue layer will overstate active work and recreate Paperclip-style false pressure.
105. Direct CEO lane-cap pressure should preserve board intent through the existing deferred-governance seam, not fall back to a hard mutation conflict. If the board is full, dropping the request recreates the same “engine knows less than the user asked” pressure ambiguity that Paperclip exposed.
106. Runtime continuity needs one bounded discriminator before it can graduate toward long-memory export. Without a field like `continuitySource`, later export or review seams would have to infer operational meaning from free-form summaries and absorbed-work strings, which is brittle and drifts toward note parsing instead of state truth.
107. Worker child-hand-off context should travel through a private execution envelope, not through public dispatch telemetry. The lane-dispatch event can stay metadata-only, but the next executor seam still needs sanitized runtime context and required capabilities after claim time or child work stays under-specified in exactly the place Paperclip used to get fuzzy.
108. Follow-on worker dispatches need the same private execution envelope as the first claimed lane. If the runtime emits only public metadata for the second step, multi-lane harness runs lose the sanitized runtime context and required capabilities exactly where the worker handoff becomes real.
109. Direct CEO lane-cap deferrals should audit what actually happened. If the new governance branch stores a bounded decision note, `hasDecisionNote` cannot stay hard-coded false or the audit/reporting trail will quietly lie about the mutation.
110. Re-dispatching an already `working` lane must stay continuity-safe. Writing a fresh `state_changed` event and resetting `continuitySource` to `state_transition` on a no-op restart fabricates history and can erase a real `resume_override` or `result_recorded` signal.
111. A worker outcome needs an explicit post-outcome decision seam even when no next lane is immediately claimable. `nextDispatch: null` can mean final assembly, governance review backlog, waiting for lane resume, or blocked-on-unblock; leaving that implicit forces the orchestrator to guess from run state and drift away from the committed harness truth.
112. A bounded post-outcome decision contract is still not enough if the runtime drops it on the floor. Once `postOutcomeAction` exists, the worker/runtime handoff should emit a dedicated non-dispatch event/hook for `queue_ceo_review`, `await_lane_resume`, and `await_unblock` so downstream logic does not quietly fall back to run-state guesswork.
113. Once non-dispatch worker outcomes have dedicated runtime handoff semantics, keep the consumers explicit too. `queue_ceo_review`, `await_lane_resume`, and `await_unblock` should stay on dedicated runtime-side handlers so later growth does not collapse them back into one generic branch with blurry follow-through.
114. Generic and specific post-outcome hooks should not share one failure boundary. If `onHarnessPostOutcomeAction` rejects after a durable lane outcome, the dedicated CEO-review / resume / unblock handlers must still run or the engine quietly loses real follow-through even though the state change already committed.
115. Runtime observability should mirror runtime control boundaries. Once CEO review, lane resume, and lane unblock have dedicated handlers, emit dedicated bounded events for them too; otherwise downstream consumers are pushed back toward parsing one generic post-outcome stream under pressure.
116. Post-outcome control truth should live behind one shared classifier. If worker orchestration and board-facing CEO follow-through each derive review/resume/unblock state with their own heuristics, they will eventually drift and recreate the same under-pressure ambiguity we were trying to cut out of Paperclip.
117. Non-dispatch worker outcomes need one durable persisted marker, not only stdout events and hooks. A bounded `attention_requested` event keeps offline consumers and later board views from having to reconstruct CEO review / resume / unblock state from raw run state after the fact.
118. Once the engine has an explicit post-outcome attention seam, the board should surface that seam directly. Making the CEO side infer “what the engine is waiting on” from lane colors or raw run state just reintroduces hidden orchestration logic at the UI boundary.
119. Playwright web-server readiness needs to verify a real app shell, not just a started Vite process. Starting Vite from the repo root with `vite apps/web ...` can still return `404` at `/`, which leaves the E2E harness timing out even though the dev server claims it is ready.
120. Reusing an existing dev server by port alone is too loose on a workstation with multiple Vite apps. Harness E2E should boot its own isolated app port or it can silently test a different repo's frontend and produce misleading failures.
121. Persisted post-outcome attention cannot stay append-only forever. If repeated identical CEO-review / resume / unblock needs always append fresh `attention_requested` events, the board history becomes noisy and the read model loses the idea of one currently unresolved attention state.
122. Attention state needs an explicit resolution event once later durable lane progress clears the prior need. Otherwise `pendingAttention` can disappear by derivation while history still looks permanently unresolved, which makes later board-memory consumers reconstruct contradictory truths.
123. Board-only pending-attention derivation and worker-emitted attention timestamps are different seams. A timestamp label like `requestedAtLabel` is only trustworthy when the attention came through persisted worker events, not when the board inferred the same control need directly from current run/card state.
124. Worker attention changes need an explicit transition shape, not just another event pair. If a lane outcome can request, resolve, or leave attention unchanged, the runtime handoff should receive that truth directly instead of diffing event history after the commit.
125. Persisted attention labels are part of the historical contract once they exist. If `attention_requested` stored a bounded status/summary/target snapshot, later board history and `pendingAttention` reads should prefer that durable snapshot over reconstructing text from whatever the lane looks like now.
126. Re-emitting generic and specific post-outcome runtime signals for unchanged unresolved attention is just a quieter form of the same noise spiral. Keep unchanged attention idempotent all the way through the runtime handoff, not only in the persisted event ledger.
127. Once the GitNexus helper is repaired, use the fallback-mode helper path deliberately and document it. The old intermittent Windows FTS crash was a tooling seam, but the fix only pays off if later slices actually prefer the stable helper invocation instead of falling back to manual seam guessing.
128. `queue_ceo_review` should not be resolved indirectly by whichever deeper helper a caller happens to pick. Once board attention explicitly says the CEO must review the run, expose a bounded review mutation that only allows the approved CEO outcomes (`complete_run` or `start_fresh_cycle`) and fail closed for other attention states.
129. `await_lane_resume` and `await_unblock` deserve the same explicit treatment as CEO review. Once the board is waiting on those attention kinds, recovery should go through bounded attention-resolution commands that update lane state and attention history together instead of generic card edits or implicit state nudges.
130. Explicit board-side attention recovery still is not enough if the resolved lane never re-enters the worker seam.
