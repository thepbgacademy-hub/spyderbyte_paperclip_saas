# Dashboard Design Prep

Date: 2026-05-07

Reference docs: `docs/design.md`, `docs/build.md`, `deploy/runbooks/deploy-poc.md`, `TODO.md`.

## Purpose

This document prepares the post-MVP Wealth Factory control panel/dashboard. The Phase 5 UI proved the core safety shape, but the production dashboard should be designed separately so customer workflows, operator controls, BYOK credentials, subscription auth, and tenant isolation are clear before implementation.

The dashboard must stay Wealth Factory-branded. It must not expose internal workflow-engine prompts, raw skill-pack names, commands, agents, tool calls, raw logs, service routes, private company mappings, or service tokens.

## Product Principles

- Make the first screen operational, not a landing page.
- Show workflow status, approved output, and next actions with dense, scannable layouts.
- Keep credential setup calm and explicit: users can add, rotate, and revoke references, but never redisplay secret values.
- Keep provider setup company-specific. Each subscribing company uses its own OpenAI, Anthropic, xAI/Grok, OpenRouter, or isolated ChatGPT/Codex subscription credentials.
- Make package installation a first-class workflow: users purchase a package, install it from the dashboard, and then operate only inside that installed package/industry.
- Keep the blank-canvas premium tier distinct: it starts with no prebuilt packages/workflows and requires the user to design the business from scratch.
- Keep the shell stable and use focused section views so the product does not collapse into one crowded dashboard.
- Treat Google Drive and Dropbox as first-class customer-owned storage destinations from the start so heavy generated artifacts can leave Wealth Factory quickly.
- Expose only business-safe workflow state and results. Raw logs, prompt echoes, skill traces, and internal runtime details remain backstage.
- Separate customer and operator surfaces by server-side authorization, not client-side role toggles.
- Treat all diagnostic detail as privileged. Customer views show SpyderByte-safe status codes and sanitized summaries only.
- Make every destructive or broad action auditable.

## Customer Dashboard Information Architecture

Primary navigation:

- Home
- Workflows
- Results
- Skills
- Profiles
- Keys
- Package
- Files
- Assistant
- Billing
- Settings

Navigation notes:

- `Assistant` is a bounded operational guide, not a general-purpose chatbot.
- `Skills` is the customer-facing surface for the employees that ship with the package plus purchased hires and marketplace browsing. It must never expose internal skill packs or hidden prompt bundles.
- `Profiles` is the company/workspace selector inside the tenant's allowed package family. It should feel like changing operating context, not like impersonation.
- `Keys` is the customer-facing BYOK and storage setup surface. It should stay calm and non-technical while still letting the user choose providers, keys, subscriptions, and storage destinations.
- `Package` is acceptable customer-facing language if page copy makes clear that it represents the installed business system and entitlements.
- We do not need to expose every configuration category shown in the reference product. Wealth Factory should ship a simpler, safer subset.

### Home

Purpose: provide a clean operational overview without becoming a cluttered system console.

Expected sections:

- Current Focus
- Needs Attention
- Operating Snapshot
- Work Queue
- restrained metrics row

Rules:

- Home can be the densest page, but every other primary page should be calmer and more task-specific.
- Home should show business decisions and next actions, not backend mechanics.
- Right-rail context should stay supportive: schedule, alerts, expiring downloads, and reminders.

### Package

Purpose: let companies purchase, install, and manage Wealth Factory packages.

Expected data:

- Package ID generated by Wealth Factory
- Package name
- Industry/category
- Package type: industry, blank-canvas, add-on employee, add-on workflow/template
- Subscription requirement
- Installed status
- Included workflows count
- Included base employees
- Allowed asset groups, shown only as public labels such as templates, scorecards, checklists, or playbooks
- Available specialist add-ons

Rules:

- A tenant can install only packages it purchased or is entitled to use.
- A tenant can have one primary installed package unless a later product decision supports multi-package companies.
- Installed package determines the allowed workflow/industry boundary.
- Blank-canvas package starts with no prebuilt workflows.
- Package IDs shown to users are Wealth Factory IDs, not Paperclip IDs.
- Prompt/rule/internal asset names are not shown to customers.
- Public package asset labels are descriptive Wealth Factory labels, not Paperclip prompt/skill/command names.

### Workflows

Purpose: let tenant members run approved workflows.

Expected data:

- Workflow ID generated by Wealth Factory
- Workflow name and description
- Installed package ID and public package name
- Required provider lane, such as OpenAI, Anthropic, xAI/Grok, OpenRouter, or company-isolated ChatGPT/Codex subscription
- Availability state, such as active or disabled
- Last run status and timestamp

Rules:

- Do not show private workflow-engine IDs.
- Do not show prompt, skill, command, or agent configuration.
- Only display workflows enabled for the authenticated tenant.
- Only display workflows included in the tenant's installed package or purchased add-ons.
- Never let a workflow run outside the tenant's installed package/industry boundary.
- Workflow execution must pull prompts, rules, templates, employees, and private assets only from the installed package's allowed asset registry.

### Results

Purpose: show outcomes, approvals, and exports without exposing internal run mechanics.

Expected data:

- Result ID generated by Wealth Factory
- Workflow name
- Status badge
- Sanitized summary
- Output readiness
- Export/download status
- Created and updated timestamps

Rules:

- Result pages should feel quieter than Home and focus on one output or one result list at a time.
- The UI may show `In progress`, `Needs approval`, `Ready`, `Delayed`, or `Failed`, but not internal worker states.
- Export states should prefer customer-owned storage language such as `Sent to Google Drive` or `Sent to Dropbox`.

### Skills

Purpose: show included base roles, activated hires, and the marketplace lane for purchasable add-ons.

Expected data:

- Skill/employee ID generated by Wealth Factory
- Employee display name
- Role category, such as executive, finance, operations, marketing, legal, sales, or specialized hire
- Included/add-on status
- Package compatibility
- Monthly add-on price or included label
- Marketplace availability state

Rules:

- Base roles should stay intentionally limited. The default Wealth Factory package should ship with only 3-4 core built-ins, such as CEO, CFO, COO, and one marketing/operations lead role.
- Purchased hires and specialist personas are additional paid add-ons.
- A tenant can activate only roles included in its package or purchased as add-ons.
- Skill activation cannot unlock workflows outside the installed package/industry boundary unless that entitlement was purchased.
- Customer-facing pages should present skills as outcome-oriented personas with mini resumes and capabilities, not as raw prompt bundles or hidden skill packs.
- Marketplace browsing can live as a tab, subview, or drawer inside `Skills` instead of requiring a separate first-level navigation item.

### Profiles

Purpose: let a customer switch between the companies or operating profiles they own inside the same allowed package family.

Expected data:

- Profile ID generated by Wealth Factory
- Company/profile name
- Package family label
- Active/inactive state
- Owner or primary contact summary
- Last activity summary

Rules:

- Profiles must stay inside the tenant's authorized package family boundaries.
- Switching profiles changes the business context of the dashboard, workflows, files, and keys.
- Profiles should never expose cross-tenant data or imply operator impersonation.
- The UX should feel like selecting the business being worked on, not entering an admin backdoor.

### Run History Within Results

Run history should live inside the `Results` experience rather than as a separate first-class customer page.

Expected data:

- Run ID generated by Wealth Factory
- Workflow name
- Status: queued, running, completed, failed, timeout, cancelled
- Requested by user
- Created and completed timestamps
- Sanitized result summary
- Public-safe error code when failed, such as `tenant_paused` or `service_unavailable`

Rules:

- Results must be shaped by Wealth Factory before display.
- Activity timelines can show public-safe milestones only.
- Raw logs, tool calls, private IDs, internal request bodies, and provider responses remain hidden.
- Customers should experience runs as result history and workflow progress, not as a backend run-management console.

### Keys

Purpose: manage tenant BYOK provider references, subscriptions, and storage destinations.

Expected data:

- Provider lane
- Display label
- Wealth Factory credential ID
- Created, rotated, revoked timestamps
- Last runtime access timestamp
- Optional non-secret metadata, such as OpenAI project ID
- Theme-safe provider badge or status label

Rules:

- Never redisplay key values.
- Never share provider credentials, Codex auth homes, or subscription sessions across companies.
- Never display backend secret handles, vault paths, or raw `secretRef` values.
- Never put raw secret material in browser storage.
- Rotation creates a new reference or new version and audits the change.
- Revocation prevents new runs from resolving that provider credential.
- The page can offer customer-safe choices for which connected provider powers which workflow family, but must not leak backend routing detail.

Supported credential setup cards:

- Connect OpenAI API key, recommended.
- Connect ChatGPT/Codex subscription, advanced, company-specific login/device-code flow only.
- Connect Anthropic API key.
- Connect xAI/Grok API key.
- Connect OpenRouter API key.

The ChatGPT/Codex subscription setup must explain that the customer is authorizing their own company/user Codex account. Wealth Factory must not use a shared server/operator ChatGPT login for subscriber work.

Storage setup cards:

- Connect Google Drive
- Connect Dropbox

Storage rules:

- Google Drive and Dropbox should be first-class long-term storage options from the beginning, not a later retrofit.
- Wealth Factory stores only the minimum needed to keep workflows coherent and deliver temporary downloads.
- Large generated artifacts should be exported into customer-owned storage whenever possible.
- Browser pages must never display raw OAuth tokens, refresh tokens, vault paths, or private provider file IDs unless a later explicit product decision requires a public-safe alias.
- If the tenant has no storage connection, Wealth Factory may still provide short-lived direct downloads under the standard temporary retention policy.
- The default temporary retention target remains 24 hours unless package-specific policy says otherwise.
- Failed exports should remain visible as customer-safe statuses such as `Export failed` or `Reconnect storage`, not disappear silently.

### Theme And Appearance

Purpose: let customers choose the dashboard palette and density without exposing internal configuration complexity.

Expected data:

- current theme preset
- available theme presets
- spacing or density mode
- contrast preference, if enabled later

Rules:

- Theme choice should be customer-facing and easy to preview.
- The default palette should remain Wealth Factory branded, but users may choose from a small curated preset list.
- Theme selection must never expose raw YAML, low-level configuration sections, or internal feature flags.
- The Hermes-inspired textured dark style is a strong baseline, but Wealth Factory should reinterpret it with cleaner business-safe labels and fewer configuration choices.

### Files

Purpose: let customers review temporary outputs and send them to customer-owned storage.

Expected data:

- File or artifact ID generated by Wealth Factory
- Related workflow or result name
- File type
- Ready/download/export state
- Expiration time
- Export destination status

Rules:

- Files pages should reinforce that Wealth Factory is temporary artifact storage, not the customer's long-term media warehouse.
- After export, the page may continue showing export outcome metadata, but not raw provider file IDs or storage paths.
- Support and operators may inspect export status metadata, but not customer-owned storage credentials or raw artifact blobs unless a later audited support workflow explicitly allows it.

### Billing

Purpose: let customers see subscription state, package billing status, and add-on charges.

Expected data:

- current plan
- package subscription status
- add-on specialist charges
- renewal date
- payment issue state

Rules:

- Billing should stay focused on account health and charges, not become a generic admin settings page.
- Billing does not grant the user access outside package entitlements.

### Settings

Purpose: manage tenant-level preferences, support, team access, and audit-safe account settings.

May include:

- team access
- audit history
- notification preferences
- support links
- account preferences

Expected data:

- User ID
- Email or display name
- Tenant role: member or owner
- Joined timestamp

Rules:

- Role changes require owner/operator authorization.
- Customer-managed role changes cannot grant internal operator/admin access.
- Internal operator/admin assignment belongs in a separate server-side control plane.
- Operators can see privileged panels only after server-side authorization.
- Tenant audit views can live under Settings, but must never show raw secrets or internal workflow-engine payloads.
- Operator audit views can show richer redacted metadata, still without raw secrets or prompts.

## Operator Dashboard Information Architecture

Primary navigation:

- Tenants
- Queue
- Runs
- Credentials
- Incidents
- System Health
- Operator Audit

### Tenants

Purpose: inspect tenant state and apply emergency controls.

Actions:

- Pause tenant workflows
- Resume tenant workflows
- Disable internal workflow integration for a tenant
- Re-enable after review

Required controls:

- Server-side operator authorization
- Required reason for pause/disable actions
- Audit event for every action

### Queue

Purpose: inspect BullMQ state without exposing job payload secrets or internals.

Actions:

- View waiting, active, failed, delayed, and dead-letter counts
- Retry a failed job
- Cancel a job
- Move a job to dead-letter state

Visible fields:

- Job ID
- Tenant ID
- Workflow ID
- Run ID
- Status
- Attempt count
- Public-safe error code

Hidden fields:

- Raw job data
- Raw internal workflow payloads
- Package prompt/rule bodies
- Private package asset IDs and Paperclip asset mappings
- Provider secrets
- Codex auth/session files
- Service tokens

### Credentials

Purpose: support safe credential operations.

Actions:

- Rotate a tenant credential reference
- Revoke a tenant credential reference
- Inspect last access timestamps

Rules:

- Operators do not view raw BYOK values.
- Every runtime access and operator mutation is audited by reference.

### Incidents

Purpose: guide support response without leaking sensitive internals.

Required fields:

- Tenant ID
- Run ID
- Public-safe error code
- Timeline
- Operator action IDs

Rules:

- Incident notes must avoid raw prompts, raw logs, BYOK values, service tokens, and private workflow-engine URLs.

## Result View Design

Customer result cards should include:

- Workflow name
- Status badge
- Sanitized summary
- User-facing next action
- Timestamp

Operator result panels may add:

- Redacted adapter status
- Retry count
- Queue timings
- Internal correlation ID

Neither view may show:

- Prompts
- Package rule bodies
- Skills
- Commands
- Agent names
- Tool calls
- Raw activity logs
- Raw provider responses
- BYOK values
- ChatGPT/Codex access tokens, refresh tokens, account IDs, emails, or auth file paths
- Private workflow-engine URLs or company IDs
- Private package asset IDs or Paperclip asset mappings

## Assistant Design Rules

The customer-facing Assistant should exist as a bounded support and guidance layer over the system, not as the system itself.

Allowed:

- answer questions about the installed package
- help the user choose among approved workflows
- explain current result or connection states
- clarify next actions
- guide setup steps
- help the user phrase support requests

Not allowed:

- general off-topic chat
- creating workflows outside the installed package boundary
- exposing private backend state
- showing Paperclip prompts, raw skill-pack names, commands, agents, tool calls, or logs
- acting as an unrestricted support console

The Assistant should be grounded strictly in:

- tenant context
- installed package
- purchased hires
- approved workflows
- customer-safe DTOs

Preferred label:

- `Assistant`

The UI should present it as a guide or helper layer, not as a generic chatbot tab for arbitrary conversation.

## Support Intake Relationship

Customer support intake should be implemented as a bounded flow inside `Assistant`, not as a second unrelated customer-facing AI surface.

That means:

- `Assistant` can answer package-safe questions
- `Assistant` can shift into support-intake mode
- support-intake mode can gather issue details and open a case
- infrastructure diagnosis and repair remain internal-only

The customer should experience one coherent `Assistant`, not multiple overlapping support bots.

## Marketplace Guardrails

The marketplace should remain constrained to package-safe expansion.

Rules:

- marketplace content must be package-compatible
- placeholder-era marketplace pages should be non-transactable unless a bounded purchase/install flow is fully implemented
- a specialist or add-on cannot by itself create cross-industry capability outside the installed package boundary
- future workflow packs or package expansions must still be resolved through entitlement checks and package compatibility rules before activation

## Visibility Matrix Summary

Design all customer pages around the following rule:

- expose directly: workflow availability, safe statuses, outputs, approvals, exports, package entitlements, employee summaries
- translate: retry mechanics, queue delays, connection refresh failures, internal checkpoints
- hide completely: Paperclip names, prompts, raw skill-pack names, commands, agents, tool calls, long raw logs, internal IDs, secret handles, provider secrets, service-role mechanics

This matrix should be treated as a hard UI contract.

## Authorization And Data Contracts

Every dashboard route must be backed by:

- Supabase Auth session validation
- Tenant membership check
- Server-side role check for operator/admin routes
- RLS-backed data access for tenant-owned rows
- Service-role writes only through controlled backend methods

API responses should use SpyderByte DTOs, not database rows or workflow-engine responses directly.

Minimum DTOs:

- `WorkflowListItem`
- `WorkflowRunSummary`
- `WorkflowRunResult`
- `CredentialReferenceSummary`
- `TenantMemberSummary`
- `AuditEventSummary`
- `OperatorQueueJobSummary`
- `OperatorTenantControlSummary`
- `ProviderCredentialSummary`
- `CodexSubscriptionAuthSummary`
- `PackageInstallSummary`
- `PackageAssetGroupSummary`
- `EmployeeEntitlementSummary`

## Next Implementation Requirements

Before building the dashboard:

- Add authenticated API route layer for workflow, run, credential, audit, and operator DTOs.
- Add package catalog, package install, subscription, and add-on employee routes.
- Add package asset registry routes for operator/admin management, with customer routes limited to public package asset labels.
- Add company-specific provider credential routes for OpenAI, Anthropic, xAI/Grok, OpenRouter, and Codex subscription auth.
- Add entitlement checks before workflow run creation.
- Add asset entitlement checks before resolving any Paperclip prompt/rule/asset.
- Add server-side authorization tests for every route.
- Add Playwright tests for member, operator, and cross-tenant access.
- Add response-shape tests proving forbidden terms and internal fields are absent.
- Replace the Phase 5 role query flag with real auth-derived role state.
- Add design review screenshots for desktop and mobile.

## Open Decisions

- Whether `api.spyderbyte.cloud` remains a separate origin or moves behind `www.spyderbyte.cloud/api`.
- Whether the first production secret backend is Supabase Vault, Paperclip encrypted company secrets, or an external KMS.
- Whether owner role and billing role are separate in the MVP.
- Whether operators can impersonate tenant read-only views, and if so how that is disclosed and audited.
- Whether ChatGPT/Codex subscription auth is company-level only or can also be delegated per user inside a subscribing company.
- Whether companies may install multiple industry packages later, or whether MVP enforces one primary installed package.
- Which base employees ship with every package, and which specialists are add-ons.
- Which package assets are common/global versus strictly industry-specific.
- How package asset version upgrades are approved and rolled out to installed tenants.
- Whether `Assistant` stays a primary nav item or becomes a persistent utility button after usability testing.
- Theme selection should live under `Settings` in the MVP, with an optional lower-nav shortcut considered later only if usability testing shows strong demand.
